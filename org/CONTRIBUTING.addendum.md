## 改动 2：把「文档约定」的仓库文件部分扩充为「仓库文件规范」

**定位**：`## 文档约定` 章节中，`### 每个仓库必须包含` 这一小节的**整体替换**。

**原文**：

```markdown
### 每个仓库必须包含

- `README.md` — 项目介绍、快速开始、依赖说明
- 必要时包含 `docs/` 目录存放详细文档
```

**替换为**：

```markdown
### 每个仓库必须包含

- `README.md` — 项目介绍、快速开始、依赖说明（**强制，无例外**）
- `docs/` — 详细文档（按需）

> 文件名统一使用大写 `README.md`。Linux 与 ROS 2 环境区分大小写，
> 不要写成 `readme.md`，否则会出现「文档存在但读不到」的问题。

### `README.md` 的最低内容

| 内容 | 说明 |
| --- | --- |
| 一句话定位 | 这个仓是做什么的；若属分层架构，注明**所属层** |
| 快速开始 | 拉取 → 依赖安装 → 构建 → 运行 |
| 依赖说明 | 依赖哪些内部仓（含版本）与哪些第三方 |
| 接口说明 | 本仓对外暴露的话题 / 服务 / 参数 |
| 上下游关系 | 上游是谁、下游是谁 |

### 多仓协作推荐包含

多仓并行开发与 AI Agent 协作时，建议同时维护以下文件：

| 文件 | 职责 |
| --- | --- |
| `AGENTS.md` | AI 开发规范：约定 Agent 在本仓的协作方式与边界 |
| `plan.md` | 开发计划与进度、Before Snapshot，保证任意时刻可中断恢复 |
| `tree.md` | 目录结构说明，新人第一份读物 |
| `decision.md` | 关键工程决策日志：**fork patch、依赖换版本、破坏性接口变更必须留痕** |

### `CODEOWNERS`

每个仓库必须包含 `CODEOWNERS`，把 Review 自动分派到对应方向负责人，
**不要全部堆给队长**——多仓之后那会成为瓶颈。

> ⚠️ **两个前提，缺一则静默失效**（官方文档核实）：
> 1. **必须是每个仓库自己的 `CODEOWNERS`**。放在组织 `.github` 仓库里**不生效**——
>    默认社区健康文件的支持列表**不含 `CODEOWNERS`**。它只能位于各仓的
>    `.github/`、根目录或 `docs/`。
> 2. **被引用的 team 必须先有该仓的 Write 权限**。官方原文：team「must have write
>    permissions, **even if all the individual members of the team already have write
>    permissions** directly, through organization membership, or through another team」。
>    否则 `@ZQU-Foray/算法组` 不会被派发 review。
```

## 改动 3：「Review 要求」增补两条

**定位**：`### Review 要求` 小节，在「视觉/电控方向代码建议由**组长** Review」之后插入两行。

**原文**：

```markdown
### Review 要求

- 至少 **1 人** Review 并通过后才可以合并
- 视觉/电控方向代码建议由**组长** Review
- Review 关注：逻辑正确性、代码可读性、潜在的 Bug
```

**替换为**：

```markdown
### Review 要求

- 至少 **1 人** Review 并通过后才可以合并
- 视觉/电控方向代码建议由**组长** Review
- **跨仓库契约类改动需 ≥2 人 Review**，且必须评估**兼容性影响**（谁在依赖被改动的字段/接口）
- **依赖清单（`.repos` 等）的版本变更需 ≥1 人 Review，且必须说明换版本理由**
- Review 关注：逻辑正确性、代码可读性、潜在的 Bug
```

> 理由：上述两类改动的**影响面跨仓**。「≥1 人」是为单仓开发设计的，
> 对契约与依赖清单不足以防住「改一处、崩一片」。

## 改动 4：新增「多仓协作」小节

**定位**：在 `## 文档约定` 章节之后、`## 求助` 之前，新增一节。

```markdown
## 多仓协作

当项目拆分为多个仓库时，必须有一个**统一的版本锚点**，否则会出现
「赛前一周发现车跑不起来，但没人知道是哪个仓动了」。

### 三层版本机制

| 层级 | 机制 | 说明 |
| --- | --- | --- |
| 仓级 | 语义化版本 + tag | 契约类仓库尤其严格，如 `v1.3.0` |
| 引用级 | 依赖清单 **pin commit** | **不要依赖分支**（`main`/`dev` 会漂移） |
| 整机级 | **meta tag** | 依赖清单快照 + 版本清单，如 `sentry-2026-v1.0.0` |

### 依赖清单

- 多仓项目使用 **vcstool (`.repos`)** 描述依赖，**不要用 `git submodule`**
  （子模块未初始化是新人最常见的坑）
- 每次比赛 / 里程碑打一个 **meta tag**
- 排障第一步：**确认现场跑的是哪个 meta tag**

### 依赖方向

若项目采用分层架构，建议每个仓库在仓根声明所属层级，并在 CI 校验
`L(n)` 不得依赖 `L(>n)`——这是让「解耦」从文档变成事实的唯一手段。

### ROS 2 仓库的 CI

ROS 2 / colcon 工作空间仓库，除通用检查外必须在 CI 中加入构建与测试。
见 [`workflows/ci-template.yml`](workflows/ci-template.yml) 的 `build-ros2` 作业
（仓库内无 ROS 2 package 时自动跳过，可安全保留在通用模板中）。
```

## 改动 5：明确「文档类仓库」不需要三级分支模型

**定位**：`## 开发工作流` 章节，在分支示意图之后、`### 标准流程` 之前插入。

**插入内容**：

```markdown
> **例外：文档类仓库**
>
> 以 Markdown / 配置为主、**不含构建产物**的仓库（如 `.github`、`foray_docs`），
> **不需要三级分支模型**，可直接在 `main` 上提交、直接 PR 到 `main`。
>
> 三级分支的价值在于隔离「可能构建失败的开发中代码」；文档没有构建产物，
> 多一层 `dev` 只是多一次合并。
```

> 理由：原规范「不要在 main 分支做任何 push 和 merge」是**无条件**表述，
> 而组织内 `.github`、`docs` 这类纯文档仓库本就不适用三级分支。
> 不写明例外，会出现「规范说不行、但实际只能这么做」的尴尬——
> 这正是规范被绕过的一种常见起点。
