# 决策层接口规范与执行计划

> 编者：RyanZzzz
> 目标：规范决策层接口（RL 与决策树同构）→ 红队 RL 验证规则 → 实战数据闭环
> 定位：本文档是 `upper_computer_architecture.md` 的**执行篇**，只讲"怎么做"

---

## 0. 一个关键洞察：决策层仿真不需要物理引擎

这是整个计划可行性的基础。

**决策层消费的是 `WorldSnapshot`（区域级抽象状态），不是原始传感器数据。** 因此：

> 对局仿真 = **一个随机博弈（stochastic game）模型**，不是物理仿真。

| 需要建模 | 不需要建模 |
|---|---|
| 场地拓扑（区域图 + 转移时间矩阵） | 物理引擎 |
| 机器人（位置/HP/弹药/冷却/速度） | 渲染 |
| 命中概率模型 + 伤害 + 飞行时间 | 真实弹道积分 |
| 裁判规则（回血/复活/阶段/胜负） | 真实点云 / 图像 |
| 观测模型（可见性 + 噪声 + 延迟） | 传感器仿真 |

**把"Gazebo 里跑 3v3"换成"一个带随机命中率的抽象对局模型"**，
工作量从"一个学期"降到"几周"，且从"千万局并行训练"变成完全可行。

> 代价：抽象仿真的保真度依赖参数准确 —— 这正是 §5「赛后用真实数据校准仿真」要解决的问题。
> 这个设计把"数据采集"从锦上添花变成了**必要环节**，闭环成立。

## 1. 决策层接口规范（P0，本周可做，不需要仿真）

### 1.1 统一签名

```cpp
Decision decide(const WorldSnapshot & world, const ActionMask & mask);
```

**三件套**：`WorldSnapshot`（态势）· `ActionMask`（可行性）· `Decision`（产物）

### 1.2 为什么 `mask` 必须进接口（关键设计决策）

因为 `(state, mask) → action` 正是 **masked policy** 的标准形式。
把 mask 放进接口，让四种实现**结构上完全同构**：

| 实现 | 如何映射 |
|---|---|
| 有限状态机 | 内部状态 + snapshot → skill |
| 行为树 | 树的行为节点输入 = snapshot + mask |
| 效用打分 | 每个 skill 算分 → 在 mask 内 argmax |
| **RL 策略** | snapshot(定长向量) → 网络 → logits → **mask → 采样/argmax** |

**收益**：
- 对 RL：mask 逻辑训练与部署**共用同一份代码** → 直接消除"训练-部署不一致"这一最大的 RL 工程坑
- 对规则：mask 即"前置条件检查"，避免选出不可行技能
- **两者共用同一个 mask 计算函数（由技能层 L5-b 提供）**，不重复实现

### 1.3 `WorldSnapshot` 字段分区

原则：**固定维度 + 缺失用 valid 标志 + 优先离散化 + 带信息年龄与置信度**。

**A. self（自身）**
| 字段 | 说明 |
|---|---|
| `region_id` | **所在区域 ID（离散化）** ← 关键，见 §1.5 |
| `pos_in_region` | 区域内归一化位置（可选，0–1） |
| `yaw`, `v` | 朝向、速度（归一化） |
| `hp`, `hp_max` | 血量 |
| `ammo` | 剩余弹丸 |
| `alive` | 是否存活 |
| `respawn_timer` | 复活倒计时 |
| `buff_state` | 增益状态位域 |

**B. allies[2]（队友，固定 2 台）**
| 字段 | 说明 |
|---|---|
| `valid` | 信息是否有效（通讯可能丢失） |
| `age` | **信息年龄（秒）** ← 决策器需知道信息多旧 |
| `region_id`, `hp`, `alive` | 状态 |
| `robot_class` | 步兵 / 英雄 |

**C. enemies[3]（敌方，固定 3 槽，按置信度降序）**
| 字段 | 说明 |
|---|---|
| `valid` | 该槽是否有目标 |
| `region_id` / `pos` | 位置 |
| `hp_estimate` | 估计血量（未知时 `valid_hp=false`） |
| `confidence` | **置信度** |
| `source` | 来源枚举：`OWN_VISION` / `SENTRY_SHARED` / `FUSED` |
| `age` | 信息年龄 |

**D. game（比赛）**
`phase`（准备/战斗/结算）· `time_left` · `own_base_hp` · `enemy_base_hp` · `score`

**E. context（派生）**
到各关键区域的转移时间（查预计算距离矩阵）· 人数优势 · 威胁度

**F. temporal（时序）**
`last_skill_id` · `last_skill_duration` · `time_since_last_damage` · `time_since_last_fire`

### 1.4 `ActionMask`

```
feasible[SKILL_COUNT] : bool
reject_reason[SKILL_COUNT] : enum（调试用）
```
由**技能层**计算（前置条件：血量 / 弹药 / 位置 / 比赛阶段 / 目标存在性）。

### 1.5 `Decision`

```
skill_id : enum
params   : 按 skill 定义（如 target_region_id / target_enemy_index）
confidence: float（可选）
rationale : 调试字段（规则=打分明细 / RL=action_prob+value）
```

### 1.6 四条设计原则（照做）

1. **定长**：不用变长数组（RL 需固定输入）；缺失用 `valid` 标志。
2. **区域离散化优先**：用区域 ID 代替原始坐标 → 降维 + **大幅缩小 sim2real gap**。
   > 这是**关键耦合**：区域化状态设计 → 使轻量对局仿真成为可能 → 使红队 RL 可行。
   > 若状态用原始连续坐标，轻量仿真立刻变得困难。
3. **带 `age` 与 `confidence`**：让决策器知道信息**多旧**、**多可信**。
4. **纯函数、零 ROS 依赖**：可单元测试、可被仿真与实车共用（对齐 RMOSS「算法与 ROS 分离」）。

## 2. 轻量对局仿真（P1）

### 2.1 最小建模集合

| # | 建模项 | 说明 |
|---|---|---|
| 1 | **场地拓扑** | 区域图 + 区域间**转移时间矩阵**（预计算） |
| 2 | **机器人** | 区域位置、HP、弹药、冷却、移动速度 |
| 3 | **射击** | 命中概率模型 `p(距离, 目标状态)`、伤害、飞行时间、弹药消耗 |
| 4 | **裁判规则** | 回血、复活、比赛阶段、胜负判定 |
| 5 | **观测模型** | 可见性（视距/视野角/遮挡）+ 噪声 + 延迟 |
| 6 | **延迟模型** | 决策周期、通信延迟、执行延迟 |

### 2.2 硬性要求

- **输出 `WorldSnapshot` 的 schema 必须与 P0 完全一致**（这就是"仿真可复现"的具体含义）
- 无渲染、可并行、相同随机种子可复现
- **单局耗时 << 1 s**（否则千万级训练不可行）

### 2.3 验收

- 能跑完一场完整 3v3 对局，输出胜负 + 关键事件序列
- 相同随机种子 → 完全相同结果
- 单局耗时满足并行训练需求

## 3. 规则决策器接入（P2）

把规则决策器实现为 §1.1 的统一接口。

**验收**：**同一份规则代码**，既能在仿真里打完整场，又能在实车上运行，行为一致。
（这是"接口规范化"是否真正落地的唯一检验。）

## 4. 红队 RL（P3，与 P2 并行）

### 4.1 流程

```
1. 规则决策器 = 我方 3 台的 policy（P2 产出）
2. 红队 RL 控制敌方 3 台：状态 = WorldSnapshot，动作 = masked skill，奖励 = 胜负 (±1)
3. 训练红队至收敛
4. 评估：红队 vs 规则，跑 N 万局
   → 统计胜率 + 收集「规则落败的状态」
5. 人审 triage（见 §4.3）
6. 修规则 → 回到 3（红队需重新训练，因为它已过时）
```

**第 6 步即对抗性课程循环**：规则变强 → 红队重新适应 → 发现新弱点。

### 4.2 对手池（防过拟合）

保留 **3–5 个历史红队检查点**，规则必须同时对抗整个池子。
否则规则会过拟合到"最新红队"，而不是变强。

### 4.3 triage：红队的发现是**候选**，不是结论

红队会同时产出三类结果，必须人工分类：

| 类别 | 处置 |
|---|---|
| ✅ **真实弱点** | → 进规则待办，修补 |
| ⚠️ **仿真 artifact** | → 记录，可能需要修仿真参数（不可能在真实中发生） |
| 🚫 **规则违规策略** | → 收紧红队动作空间（红队钻了规则漏洞） |

**控制点**：红队必须被限制在**与真实对手相同的动作空间与能力范围**内。
否则它找到的是"规则漏洞"而非"真实弱点"。

### 4.4 红线

- 红队是**支线**：赛前没做完不影响交付
- 红队输出**只用于改规则**，不直接上实车
- 红队**永远待在仿真里** → **不需要 sim2real** ← 这是它风险为零的根本原因

## 5. 实战数据采集（P4，必须**赛前**就做好）

> ⚠️ **格式必须现在定。赛后补不了——字段没记，数据就永久作废。**

### 5.1 采集清单（按重要性）

| # | 层 | 内容 |
|---|---|---|
| 1 | **决策层** | `(world_snapshot, mask, chosen_action, confidence)` 每决策周期 |
| 2 | **感知层** | 定位位姿 + 置信度；敌方检测（位置/置信度/来源）；残差检测结果 |
| 3 | **执行层** | 底盘指令、云台指令与实际角度、射击事件 |
| 4 | **裁判系统** | 原始报文（血量/弹药/阶段/胜负） |
| 5 | **元数据** | 统一时间戳、比赛 ID、**地图版本**、**代码版本(git hash)**、**参数版本** |

### 5.2 对齐要求

- **统一时钟**（对齐 X3 时间同步面）
- 单场比赛 = **一个 episode**，可完整重放

### 5.3 验收

赛后能回答：**"第 3 分 12 秒，决策层在什么状态下选了技能 X，为什么？"**

（对齐同济 sp_vision_25 的目标："赛前问题排查、赛后问题重现"。）

## 6. 赛后闭环（P5）—— 一处重要修正

### 6.1 修正：真实数据的最高价值用途**不是直接训练 RL**

**为什么**：
- 直接训 RL = offline RL，需要**大量**数据，且有分布偏移（extrapolation error）问题
- 一个赛季可能只有几十场比赛的数据，**量级远远不够**

**应该怎么做**：用真实数据做 **system identification（系统辨识）**——

> 辨识命中率分布、移动速度、决策延迟、通信延迟、观测噪声的**真实参数**，
> 然后灌进仿真的射击/观测/延迟模型。

**收益**：仿真越可信 → 红队越有效 → 规则修补越准
⇒ **而且主线的导航/感知测试同样受益**（仿真保真度是共同需求）

### 6.2 优先顺序

| 优先级 | 用途 | ROI |
|---|---|---|
| **1** | **校准仿真**（拟合仿真参数） | **最高** |
| **2** | **规则修补**（用红队失败清单改规则） | 直接见效 |
| 3 | 离线策略评估（offline RL / 反事实评估） | 数据足够后再考虑 |
| 4 | 在线 RL | 远期，需巨大投入 |

## 7. 序时计划与验收

| 阶段 | 工期 | 产出 | 验收标准 |
|---|---|---|---|
| **P0 接口冻结** | ~1 周 | `WorldSnapshot` / `ActionMask` / `Decision` schema + **区域划分表** | 规则决策器与 RL 能用**同一签名**实现（先写两个 mock 验证） |
| **P1 轻量对局仿真** | ~2 周 | 无渲染 3v3 对局仿真 | 单局 << 1s；同种子可复现；state schema 与 P0 一致 |
| **P2 规则接入** | ~1 周 | 规则决策器实现统一接口 | **同一份代码**在仿真与实车行为一致 |
| **P3 红队 RL** | 并行 2–4 周 | 红队策略 + 人审后的规则失败清单 | 红队胜率显著高于随机；≥N 条被确认为真实弱点 |
| **P4 数据采集** | 赛前 | 统一记录格式 + 回放工具 | 一场训练赛后可完整重放决策过程 |
| **P5 赛后闭环** | 赛后 | 校准后的仿真参数 + 修补后的规则 | 规则对红队胜率提升；仿真与实车胜率差异缩小 |

### 7.1 关键：每一块产出对主线都有独立价值

这是本计划风险低的根本原因——**即使永远不做 RL，这些产出也不浪费**：

| 产出 | 不做 RL 时的用途 |
|---|---|
| 接口规范化（P0） | 规则决策、单元测试、模块解耦、回归测试 |
| 轻量对局仿真（P1） | **规则调参**、战术演练、参数寻优 |
| 数据采集（P4） | 复盘、问题重现、规则修补、故障定位 |
| 仿真校准（P5） | **主线导航/感知测试的保真度** |

⇒ **没有任何一块是"为 RL 服务的沉没成本"。**

### 7.2 人力建议

| 角色 | 职责 |
|---|---|
| 1 人 | 接口规范 + 轻量对局仿真（**主线必需**，非 RL 专属） |
| 1 人 | 红队 RL（支线） |
| 主线组 | 不受影响 |

## 8. 立即可以开始的三件事（本周）

1. **划区域**：把 3v3 场地划成区域图，产出区域 ID 表 + 转移时间矩阵
   （不需要任何代码，找张场地俯视图就能开始）
2. **起草 schema**：按 §1.3~§1.5 写出 `WorldSnapshot` / `ActionMask` / `Decision` 的字段清单
3. **写两个 mock**：一个"永远选巡逻"的规则 decider，一个"随机在 mask 内选"的 RL decider
   → 验证**统一签名真的能容纳两者**（这是 P0 的验收标准，且一天内可完成）

> 这三件事**不依赖仿真、不依赖 RL、不依赖任何硬件**，本周即可启动。
