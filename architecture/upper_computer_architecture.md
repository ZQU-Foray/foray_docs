# 上位机算法架构总纲（宏观骨架 v1.0）

> 编者：RyanZzzz
> 面向：ZQU-Foray 战队
> 目标：功能解耦 · 兵种高复用 · 模块边界清晰 · 接口高效 · 可扩展可持续
> 范围：**只做宏观骨架与契约，不做详细代码生成**

---

## 0. 结论摘要

原方案（layer0 I/O → layer1 决策+看门狗 → layer2 应用 → layer3 工具）方向正确，但混用了**三种不同性质的维度**，导致三处结构性错误：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 层号方向不自洽：决策(1) 排在 应用(2) *之下* | 决策依赖倒置，权限仲裁无处安放 |
| 2 | 把「横切关注点」当「层」：看门狗、调试 | 每个模块被迫依赖监管/调试，耦合成网 |
| 3 | **缺失装配根（composition root）层** | 兵种复用没有落点，"复用"只能靠 `#ifdef` |

修正后的骨架 = **6 个纵向层（L0–L5，依赖单向向下）+ 4 个横切面（X1–X4，贯穿所有层）+ 1 个装配根轴（R，兵种差异的唯一落点）**。

「调试与中间件冲突吗？」——**不冲突**。中间件是*传输机制*，调试是*可观测性能力*，二者正交。真正的冲突是"调试代码污染生产实时路径"，解法见 §6。

## 1. 调研依据（一手证据）

本骨架不是凭经验臆造，而是对齐了以下四类一手资料：

### 1.1 RMOSS —— RM 社区唯一的官方架构设计文档
- [RMOSS 基本设计模式](https://github.com/robomaster-oss/rmoss_tutorials/blob/main/docs/design/rmoss_design.md)
- [RMOSS 项目规范](https://github.com/robomaster-oss/rmoss_tutorials/blob/main/docs/developer_guides/rmoss_project_spec.md)
- [robomaster-oss/rmoss_core](https://github.com/robomaster-oss/rmoss_core)

给出的三层模型 **Hardware Layer → Interface Layer → Task Layer**，并把任务模块显式分为三类：
**接口任务模块 / 功能任务模块 / 决策任务模块**，其中
> "决策任务模块：面向机器人全局决策，**管理并利用控制任务与功能任务**的模块节点。"

→ 决策在功能任务**之上**，这是原方案倒置的直接反证。

RMOSS 还有两条必须继承的原则：
1. **算法与 ROS 分离**：每个模块 = 「算法/驱动实现（零 ROS）」+「ROS 顶层适配（仅通信）」。
   好处：可单元测试、可"去 ROS 化"降开销、可整体塞进一个进程。
2. **C/S 任务管理模型**：决策节点通过 service 管理其他模块，状态仅 `RUNNING/IDLE/ERROR`，命令仅 `START/STOP`
   （`GetTaskStatus.srv` / `ControlTask.srv`）。并明确注释：
   > "相比于 `rclcpp_lifecycle::LifecycleNode`，该方式更加简单。"

### 1.2 同济 sp_vision_25（617★）——"一套框架 × 多兵种"的现成范本
- [TongjiSuperPower/sp_vision_25](https://github.com/TongjiSuperPower/sp_vision_25)

它的目录本身**就是**分层，且直接回答了"兵种复用怎么做"：

| `io/` | I/O 层 | camera / cboard / gimbal / dm_imu / socketcan / serial / hikrobot / mindvision / **ros2（与导航互通的桥）** |
| `tasks/` | 功能层 | auto_aim（detector · classifier · yolo · armor · target · tracker · voter · aimer · solver · shooter · planner）、auto_buff、omniperception（perceptron · decider · detection） |
| `tools/` | 工具层 | crc · exiter · EKF · img_tools · logger · math_tools · pid · plotter · ransac · recorder · thread_pool · thread_safe_queue · trajectory · yaml |
| `src/` | **装配根** | `sentry.cpp` · `standard.cpp` · `standard_mpc.cpp` · `uav.cpp` · `sentry_bp.cpp` · `sentry_multithread.cpp` · `mt_standard.cpp` + 各自 `*_debug.cpp` |
| `configs/` | 配置 | `sentry.yaml` · `standard3.yaml` · `standard4.yaml` · `uav.yaml` · `ascento.yaml` · `camera.yaml` · `calibration.yaml` |
| `calibration/` | 离线工具 | 相机标定 · 手眼标定 · 机器人世界系手眼标定 · 采集 · 视频切分 |
| `tests/` | 独立测试 | 22 个**单独可执行**的模块测试（camera / cboard / gimbal / detector_video / fire / handeye / planner / topic_loop …） |

**关键结论：兵种复用 = 同一套 `io/` + `tasks/` + `tools/`，配不同的 `src/` 装配根与 `configs/` YAML。**
不是靠宏，不是靠继承，是靠**组合根 + 配置**。而且 `src/` 每个兵种都是极薄的一层 main。

它的 readme 还自述：自瞄是**分布式软件**——识别器/估计器/决策器在小电脑，控制器在 MCU，
"模块划分解耦了视觉组和电控组的职责"。这对我们的人员分工同样成立。

### 1.4 Autoware —— 工业级分层参照 + 横切面的标准答案
- [Architecture overview](https://github.com/autowarefoundation/autoware-documentation/blob/main/docs/design/autoware-architecture-v1/index.md)

它的自我陈述与我们的目标几乎逐字重合：
> "a layered architecture that clarifies each module's role and simplifies the interface between them …
> users can easily replace an existing module with their own software component by simply wrapping their software to fit in with Autoware's interface."

七个纵向栈：Sensing · Map · Localization · Perception · Planning · Control · Vehicle Interface。

**最有价值的一条**：v1 架构文档明确把
> Fail safe · HMI · Real-time processing · Redundant system · **State monitoring system**

列为**架构之外、后续工作**——然后通过 [AD API](https://github.com/autowarefoundation/autoware-documentation/tree/main/docs/design/autoware-architecture-v1/interfaces/ad-api/features) 以**横切接口**的形式补回来：

| 横切能力 | Autoware 的设计 |
|---|---|
| [heartbeat](https://github.com/autowarefoundation/autoware-documentation/blob/main/docs/design/autoware-architecture-v1/interfaces/ad-api/features/heartbeat.md) | 消息含 **timestamp + sequence number**，用于检测通信延迟、乱序、丢包 |
| [fail-safe](https://github.com/autowarefoundation/autoware-documentation/blob/main/docs/design/autoware-architecture-v1/interfaces/ad-api/features/fail-safe.md) | **一道 gate**：在"正常指令"与"异常指令(MRM)"之间切换。状态机 `NONE/OPERATING/SUCCEEDED/FAILED`；含 RTI(请求接管) / MRM(最小风险行为) / MRC |
| [diagnostics](https://github.com/autowarefoundation/autoware-documentation/blob/main/docs/design/autoware-architecture-v1/interfaces/ad-api/features/diagnostics.md) | 功能单元的**故障树(DAG)**，error level 同 `diagnostic_msgs/DiagnosticStatus`；**静态结构只发一次 + 动态状态周期发**；级别可 **latch**（持续异常后不自动恢复）并提供 reset |
| [operation_mode](https://github.com/autowarefoundation/autoware-documentation/blob/main/docs/design/autoware-architecture-v1/interfaces/ad-api/features/operation_mode.md) | 模式状态机 Stop / Autonomous / Local / Remote + `is_autoware_control_enabled` + `change_to_*` 可行性标志 |

**"一道安全门 (gate)"是整个监管设计的核心抽象**——它不在数据流里，而是**仲裁"谁有权发指令"**。
这正是原方案"看门狗模块"应该长成的样子。

另参考其 [ROS 节点类设计规范](https://github.com/autowarefoundation/autoware-documentation/blob/main/docs/contributing/coding-guidelines/ros-nodes/class-design.md)：
node 类继承 `rclcpp::Node`、构造函数显式接受 `NodeOptions`、
并以 `RCLCPP_COMPONENTS_REGISTER_NODE` 注册 —— **让"可组合"成为默认属性而非事后改造**。

### 1.5 中间件侧的官方事实（决定"接口高效"怎么落地）
- [Executors](https://docs.ros.org/en/humble/Concepts/Intermediate/About-Executors.html)：Executor 决定回调跑在哪个线程；`SingleThreadedExecutor` 是最简形态，可换成多线程 / 自定义。
- [Intra-Process Communication](https://docs.ros.org/en/humble/Tutorials/Demos/Intra-Process-Communication.html)：
  进程内 pub/sub 配合 `std::unique_ptr` 发布可实现 **零拷贝**（官方 demo 用同一内存地址证明）。
- [Composition](https://docs.ros.org/en/humble/Tutorials/Intermediate/Composition.html)：多节点同进程 + `ros2 component load` 动态装载。
- [QoS](https://docs.ros.org/en/humble/Concepts/Intermediate/About-Quality-of-Service-Settings.html)：
  `reliability`(reliable/best_effort) · `durability`(volatile/**transient_local ≈ latching**) ·
  `deadline` · **`liveliness`（"losing liveliness could be an indication of a failure"——内置的看门狗原语）** · `history/depth`。
  官方 sensor data profile = best effort + 小队列。
- REP 规范：[REP-103](https://www.ros.org/reps/rep-0103.html)（单位与坐标轴）、[REP-105](https://www.ros.org/reps/rep-0105.html)（移动机器人坐标系）。

## 2. 对原方案的三处结构性诊断

### 2.1 层号方向不自洽 → 决策被埋在应用之下 + 层级倒置

原方案：`layer0 I/O → layer1 决策/看门狗 → layer2 应用 → layer3 工具`

三个维度被塞进一条编号：
1. **抽象层级**（越往上越"智能"）：I/O → 状态 → 功能 → 决策
2. **横切关注点**（没有层级，只有"贯穿"）：看门狗、调试、时间、配置、接口契约
3. **装配/组合**（不是"层"，是"根"）：兵种差异

具体后果：
- **决策必须在功能之上**（RMOSS 原文、Autoware 的 planning/control 与 fail-safe gate 均如此）。原方案把决策放 layer1、应用放 layer2，导致"应用调用决策"或"决策与应用同层互调"，权限仲裁（自瞄接管云台 vs 遥控接管云台）没有位置。
- **"感知"与"自瞄/导航"不是同级**。原方案 layer2 把它们并列，但按你自己导航设计文档 §2 的数据流：
  `驱动 → 状态估计 → 定位 → 地形/代价 → 规划控制`。
  感知是**自瞄与导航共同的下游依赖**，应在它们**之下**。
- **工具层放最顶（layer3）方向反了**。工具（math/EKF/logger/CRC）是**最底层、最稳定、被所有人依赖**的，应在最下面。

### 2.2 把横切关注点当"层" → 耦合成网

「看门狗」被列为 layer1 的模块 2，意味着**每个模块都要认识看门狗**。
但看门狗/健康监管的本质是：模块**自报**健康（统一接口），监管者**订阅**并**仲裁**。
若做成层，就会退化成"每个模块 include 看门狗头文件"——这是耦合爆炸，且必然出现循环依赖。

Autoware 的处理方式是决定性的证据：它**没有**把 state monitoring 做成层，而是在架构文档里声明其为层外事项，再用 AD API 的横切接口补齐。
RMOSS 同样把任务管理做成 `rmoss_interfaces` 里的 service，而不是一个层。

### 2.3 「调试模块与中间件冲突」——伪冲突，但直觉有价值

**为什么是伪冲突**：
| | 中间件 | 调试 |
|---|---|---|
| 本质 | **传输机制**（发现、序列化、QoS、执行模型） | **可观测性能力**（记录、复现、可视化、调参） |
| 关注问题 | 数据怎么从 A 到 B | 我怎么知道它对不对、为什么不对 |
| 二者关系 | 正交，调试**消费**中间件的数据流 | |

**但你的直觉有价值**——真正的冲突在另一处，而且必须解决：

> **调试代码会污染生产实时路径。** 把 `plotter` / `logger` 塞进自瞄的 100FPS 主循环，就是在实时路径上加锁和 IO。

同济 sp_vision_25 的解法值得直接抄：
- **调试入口独立**：`sentry_debug.cpp` 与 `sentry.cpp` 并存，是**不同的装配根**，不是 `#ifdef`
- **可观测性基础设施下沉**：`tools/logger` · `tools/recorder`（rosbag 式的"时间戳+视频+四元数"录制，可离线复现）· `tools/plotter`
- **模块独立测试**：22 个单独可执行文件
- 可视化/调参走**外部工具**：PlotJuggler / rviz2 / NoMachine 远程桌面

所以「调试模块」其实是三样东西，要分别归位：
1. **可观测性基础设施** → 下沉到 L0（平台基础层）
2. **调试装配根 / 独立测试程序** → 归 R（装配根轴），与生产装配根并列
3. **可视化与在线调参** → 归 X4（可观测与调参面），且优先用外部工具，不写进业务代码

## 3. 修正后的宏观骨架

### 3.1 总图

```
┌───────────────────────────────────────────────────────────────────────────┐
│ R  装配根轴（兵种差异的唯一落点，唯一允许"知道全局"的地方）                    │
│    sentry_root · standard_root · hero_root · uav_root · radar_root         │
│    launch 装配 · 参数分层覆盖 · namespace · sim/real · 生产根 ∥ 调试根 ∥ 测试根 │
└───────────────────────────────────────────────────────────────────────────┘
                                    ▲ 组合 L0–L4
┌───────────────────────────────────────────────────────────────────────────┐
│ L5 决策与仲裁层                                                             │
│    全局战术决策（行为树/状态机，策略数据化 XML/YAML，插件化叶子节点）          │
│    指令仲裁安全门 Gate（谁有权控制底盘/云台/发射机构）                        │
└───────────────────────────────────────────────────────────────────────────┘
                                    ▲
┌───────────────────────────────────────────────────────────────────────────┐
│ L4 功能应用层（每个功能 = 独立 package，可独立启停/测试/回放）                 │
│    自瞄 auto_aim · 能量机关 auto_buff · 导航 navigation · 雷达站 radar        │
│    ← 每个功能自带"局部决策"（aimer/shooter 决策、nav recovery）               │
└───────────────────────────────────────────────────────────────────────────┘
                                    ▲
┌───────────────────────────────────────────────────────────────────────────┐
│ L3 状态与感知层（输出带时间戳·置信度·新鲜度的世界模型）                        │
│    状态估计(里程计/IMU融合) · 定位与地图(重定位/地图服务)                     │
│    赛场态势(裁判系统/RFID/比赛阶段/敌我信息融合) ← 原方案缺失                 │
│    环境感知(地形/代价/障碍) · 目标感知(装甲板检测跟踪)                        │
└───────────────────────────────────────────────────────────────────────────┘
                                    ▲
┌───────────────────────────────────────────────────────────────────────────┐
│ L2 I/O 抽象层（全部以"接口/端口"形式暴露，实现可替换）                        │
│    下行 HAL：传感器驱动(相机/雷达/IMU) · 执行器抽象(底盘/云台/发射机构)        │
│              总线抽象(串口/CAN/USB) · 设备生命周期(open/close/recover)       │
│    上行中间件端口：pub/sub/srv/action 的抽象 · QoS 档位 · 执行器与回调组策略    │
│    横向机间通信端口：网络传输 + 统一态势语义（独立于具体 DDS 实现）             │
└───────────────────────────────────────────────────────────────────────────┘
                                    ▲
┌───────────────────────────────────────────────────────────────────────────┐
│ L1 平台基础层（零业务语义，被所有人依赖，最稳定）                              │
│    时间与时钟 · 数学/几何/滤波(EKF/PID) · 数据结构(无锁队列/线程池)            │
│    参数系统(类型化 schema+校验+热加载) · 错误码与结果类型 · 日志/录制/回放基础设施│
└───────────────────────────────────────────────────────────────────────────┘

╔═══════════════════════════════════════════════════════════════════════════╗
║ 横切面（贯穿 L1–L5，不是"层"；以契约与能力形式提供，禁止反向依赖）             ║
║  X1 健康与安全监管面   X2 接口契约面   X3 时间与同步面   X4 可观测与调参面     ║
╚═══════════════════════════════════════════════════════════════════════════╝
```

> 层号约定：**数字越大越靠近"智能与策略"，依赖严格单向向下**。
> L2 的 HAL 采用依赖倒置——抽象接口在 L2，具体驱动实现可放 L2 之下的插件目录，但依赖方向仍是"实现依赖抽象"。

### 3.2 与原方案的逐条映射

| 原方案 | 修正后归属 | 说明 |
|---|---|---|
| layer0 模块1 中间件（向上 I/O） | **L2 上行中间件端口** | 保留，但必须是**抽象端口**而非"到处直接用 ROS2"；否则无法单测、无法去 ROS 化、无法换中间件 |
| layer0 模块2 硬件抽象（向下 I/O） | **L2 下行 HAL** | 保留。补：设备生命周期与自恢复（RMOSS 的 `ERROR` 态尽量自修复） |
| layer0 模块3 机间通信（横向 I/O） | **L2 横向端口 + L3 态势语义 + X2 契约** | 拆三份：传输属 L2；"赛场态势"是共享世界模型属 L3；消息/协议版本属 X2。机间通信不是与 HAL 平级的"设备 I/O" |
| layer1 模块1 决策 | **L5 决策与仲裁**（上移） | 且拆成两层语义：全局战术决策 + 指令仲裁 Gate；局部决策下沉进 L4 各功能 |
| layer1 模块2 看门狗 | **X1 横切面**（拆 4 件） | 不设层。见 §4 |
| layer2 模块1 自瞄 | **L4 功能应用** | — |
| layer2 模块2 导航 | **L4 功能应用** | — |
| layer2 模块3 感知 | **L3 状态与感知**（下移） | 它是自瞄/导航的**共同下游**，不是同级兄弟 |
| layer3 模块1 调试 | **拆三份**：L1 基础设施 + R 调试装配根 + X4 可观测面 | 见 §6 |
| （缺失） | **R 装配根轴** | 兵种复用的落点，**必须补** |
| （缺失） | **X2 接口契约面** | 接口版本化与治理，**必须补** |
| （缺失） | **X3 时间与同步面** | 多传感器时间戳/TF/仿真时钟，**必须补** |

## 4. X1 健康与安全监管面（原"看门狗"的正确形态）

原方案把 4 件不同的事揉成了一个"看门狗模块"。它们的时间尺度、实现机制、信任级别都不同，必须分开：

| 子能力 | 回答的问题 | 时间尺度 | 机制 | 参照 |
|---|---|---|---|---|
| **a) 心跳/存活** | 进程还活着吗？数据还在流吗？ | ms–100ms | 消息带 **timestamp + sequence**；用 QoS **`deadline`** 检测停流、**`liveliness`** 检测发布者失活 | Autoware heartbeat；ROS2 QoS |
| **b) 状态/故障诊断** | 哪个功能单元坏了？坏到什么程度？ | 100ms–1s | 功能单元**故障树(DAG)**；error level 沿用 `diagnostic_msgs/DiagnosticStatus`；**静态结构发一次 + 动态状态周期发**；级别可 **latch** + reset | Autoware diagnostics |
| **c) 失效安全/降级仲裁** | 现在谁有权发指令？失效时退到什么行为？ | 事件驱动 | **一道 Gate**，在"正常指令"与"降级指令(最小风险行为)"间切换；状态机 `NONE/OPERATING/SUCCEEDED/FAILED` | Autoware fail-safe RTI/MRM/MRC |
| **d) 任务生命周期管理** | 这个功能该跑还是该停？ | 事件驱动 | 决策节点以 **service** 管理功能节点（`GetTaskStatus` / `ControlTask`），状态 `RUNNING/IDLE/ERROR`，命令 `START/STOP` | RMOSS C/S 模型 |

**三条设计铁律**：

1. **自报 + 订阅，禁止反向依赖**。模块只负责"以统一接口暴露自己的健康"，绝不 include 监管者。
2. **急停必须有硬路径**。最终的安全降级（如 `cmd_vel` 超时归零、发射机构断电）**不能依赖中间件**——因为它要覆盖的正是"中间件本身挂了"的场景。放在最靠近执行器的一层（L2 执行器抽象内部），用独立的实时线程 + 超时定时器实现。
3. **B 与 C 分离**。诊断只做"报告状态"，仲裁只做"决定权限"。混在一起会导致"检测到故障就直接改指令"，无法审计、无法分级降级。

> RMOSS 已经给出 d) 的现成契约：`rmoss_interfaces` 的 `GetTaskStatus.srv` / `ControlTask.srv`；
> Autoware 给出 a)/b)/c) 的现成语义。我们只需按哨兵实际规模裁剪，不必自创。

## 5. 兵种复用的落点：R 装配根轴

这是原方案缺失、但对"各兵种代码可复用程度高"最关键的一环。

**核心命题：兵种差异不体现在代码里，而体现在"装配 + 配置"里。**

兵种差异只有三个来源：

| 差异来源 | 举例（哨兵 vs 步兵 vs 英雄 vs 无人机） | 复用机制 |
|---|---|---|
| **硬件拓扑** | 有无云台/发射机构、底盘类型（麦轮/舵轮/全向）、IMU/CAN 拓扑 | L2 HAL 抽象接口 + 可替换驱动实现 |
| **传感器配置** | 相机型号（海康/迈德威视/USB）、雷达型号、是否带雷达站 | L2 驱动插件 + X 参数系统 |
| **策略与参数** | 巡逻/进攻/回补逻辑、自旋速度、弹速、血量阈值 | L5 行为树 XML + 参数分层覆盖 |

**参数分层覆盖（推荐三级）**：
```
config/base.yaml          ← 全兵种共享（坐标系、单位、通用阈值）
   ↑ 覆盖
config/<robot_type>.yaml  ← 兵种差异（sentry / standard3 / standard4 / uav）
   ↑ 覆盖
config/<site>.yaml        ← 场景差异（sim / reality / 比赛场地）
```
这与 pb2025 生态已有的 `config/simulation` 与 `config/reality` 双目录一致，只是从两级扩展到三级。

**装配根的职责（且仅限这些）**：
- 选择并实例化模块组合
- 注入配置
- 决定进程/线程/执行器拓扑（哪些模块同进程组合、哪些独立进程）
- 设置 namespace、remap、TF 静态外参
- 切换 sim / real / 硬件在环 / 无硬件回放

**装配根禁止**：包含任何算法逻辑。同济的 `src/sentry.cpp` 与 pb2025 的 `*_bringup` 包都是极薄的，这是纪律。

## 6. 「调试」的正确归位（回答原问题）

| 调试产物 | 归位 | 原则 |
|---|---|---|
| 日志、录制/回放（rosbag/MCAP + 自定义"时间戳+视频+状态"）、指标、trace | **L1 平台基础层** | 基础设施化，被所有人复用；接口稳定；**生产构建可关闭但接口不变** |
| 调试主程序（`*_debug.cpp`）、模块独立测试可执行、无硬件回放 launch | **R 装配根轴**（与生产根并列） | 独立 composition root，**不用 `#ifdef`**；生产根绝不链接调试逻辑 |
| 可视化（rviz2/Foxglove）、曲线（PlotJuggler）、在线调参 | **X4 可观测与调参面**，优先用**外部工具** | 业务代码只暴露观测点（topic/参数/诊断），不实现可视化 |
| 参数在线调参能力 | **L1 参数系统** 提供能力，**X4** 定义使用约定 | 类型化 schema + 校验 + 热加载；危险参数需鉴权 |

**为什么这样就不冲突了**：中间件在 L2 负责"数据怎么流"，可观测性在 L1 负责"记录与复现"，调试装配根在 R 负责"以调试姿态启动"。三者职责正交，依赖方向也全部向下/向内，无环。

## 7. 接口高效：必须现在定、后期难改的 6 个决策

「接口高效」不能靠事后优化，它是架构决策。按优先级：

1. **实时域划分（最重要）**。把模块按时间尺度分成三域，并**用不同的执行模型**：
   - **硬实时域**（云台控制环、发射机构）：1ms–10ms。**去中间件**，直连 HAL，独立实时线程，禁止动态内存分配与锁。
   - **软实时域**（自瞄检测/跟踪、导航控制）：10ms–100ms。进程内组合 + 零拷贝。
   - **非实时域**（决策、态势融合、日志、诊断、可视化）：100ms–1s。可容忍中间件开销。
   > sp_vision_25 的 `sentry_multithread.cpp` / `mt_standard.cpp` 就是这个分域思路的实证。

2. **进程内组合 + 零拷贝**。把软实时域的高频链路（图像 → 检测 → 跟踪）放进**同一个 component container**，用
   `RCLCPP_COMPONENTS_REGISTER_NODE` 注册、以 `std::unique_ptr` 发布，可取得进程内零拷贝。

3. **QoS 档位化**。不要每个话题随手写 QoS。定义 2–3 个**命名档位**：
   - `sensor_data`：best_effort + 小队列（图像、点云）
   - `control_command`：reliable + `deadline` 监控（`cmd_vel`、云台指令）
   - `latched_state`：`transient_local`（地图、机器人描述、静态外参、比赛阶段）
   档位定义与"为什么这么选"必须落在 X2 契约文档里。

4. **执行器与回调组策略显式化**。哪些回调必须互斥、哪些可并行、哪些必须高优先级——写成装配根的显式配置，而不是依赖默认 `spin`。

5. **关键路径保留"去 ROS 化"能力**。遵循 RMOSS 的"算法与 ROS 分离"：算法层零 ROS 依赖，
   ROS 层只是薄适配器。这样必要时可以把多个模块合进一个进程直连调用，而不重写算法。

6. **跨模块只传语义，不传原始数据**。决策层不应订阅原始点云；它应消费 L3 输出的
   "敌方位置 + 置信度 + 时间戳"。参照 `CalculateAttackPose` 只吃 `Target` + costmap。

## 8. X2/X3/X4 三个横切面的最小契约

### X2 接口契约面
- **接口包独立于实现包**（对齐 `rmoss_interfaces` / `pb_rm_interfaces` / `auto_aim_interfaces`）。
- **语义版本化**，并**钉死外部协议版本**（如裁判系统串口协议 `V1.7.0 (20241225)`）。
- **消息设计规范**：单位与坐标系遵循 REP-103 / REP-105；必须带 `stamp` 与 `frame_id`；
  估计类消息带置信度；云台角约定必须全队统一（RMOSS 采用刚体坐标约定：**yaw 向左为正、pitch 向下为正**，
  并提示这与 DJI 的 NED 约定不同——**这个坑必须在契约里写死**）。
- **变更流程**：接口变更需评审 + 影响面清单 + 兼容期。

### X3 时间与同步面（我们最痛的地方，务必成面）
- 统一时钟源；`use_sim_time` 在 sim/real 间切换时，**所有节点行为一致**。
- **时间戳契约**：谁打时间戳、在哪个时刻打（采集时刻 / 接收时刻）、跨域传递时是否重打。
  > 你们的导航设计文档 §11 已踩过：`Twist` 无时间戳导致无法与 odometry 对齐，
  > 所以 `fake_vel_transform` 必须订阅 `local_plan` 取时间戳。这类"隐式时间契约"应显式化。
- **数据新鲜度（staleness）**：每个输入定义"多久算过期"，过期即降级。这是 X1 的输入前提。
- TF 树完整性与时间插值容差的**启动自检**（对齐你们文档的"TF 树不对，一切白搭"）。

### X4 可观测与调参面
- **观测点标准化**：统一命名约定、统一单位、统一降采样策略；高频数据必须可降采样后观测。
- **可复现优先**：录制比实时可视化更重要。目标 = "赛后能把问题重现"。
  （同济 readme 明确把"赛前问题排查、赛后问题重现"列为架构目标。）
- **调参不影响实时**：参数热加载走非实时域；危险参数需鉴权与审计。
- **可视化工具外置**：rviz2 / Foxglove / PlotJuggler，不写进业务模块。

## 9. 让解耦"可持续"的 4 条治理机制

架构文档写完就烂，是常态。必须配可执行的保障：

1. **包依赖图与方向检查进 CI**。每个 package 声明它属于哪一层（如 `layer:=L3`），
   CI 校验：`L(n)` 不得依赖 `L(>n)`；横切面不得被业务层 include 实现，只允许用其接口。
   这是"功能解耦"从文档变成事实的唯一手段。

2. **模块独立可测是硬门槛**。一个新模块必须能带一个**独立可执行测试**（同济 `tests/` 22 个；
   `rm_vision` 有 `no_hardware.launch.py`）。不能独立测的模块 = 没解耦。

3. **策略数据化**。全局策略、兵种差异、场景参数都放 XML/YAML。
   目标：**新增一个兵种行为不需要重编译，只需要新增 XML + YAML + 一个薄装配根。**
   这是"可持续发展"的具体定义，也是让新人快速上手的关键。

4. **两套入口并存**：生产装配根 与 调试装配根 都进仓库、都进 CI。禁止 `#ifdef DEBUG` 式的代码分支。

## 10. 演进路线（宏观，不含代码）

| 阶段 | 目标 | 验收信号 |
|---|---|---|
| P0 定契约 | 冻结 L2/L3 接口 + 建接口包 + 定 QoS 档位与命名规范 | 接口包可单独构建；每层归属已在 CI 可校验 |
| P1 立骨架 | 建 L1 平台基础层 + L2 HAL 抽象接口 + 一个真实驱动实现 | 能在无算法的情况下跑通"一个传感器 → 一个话题" |
| P2 打通单功能 | 选一条最短闭环（如 相机 → 装甲板 → Target）打穿 L2→L3→L4 | 该链路可独立启停、可独立测试、可回放复现 |
| P3 装配根 | 建 R：一个生产根 + 一个调试根 + 一个无硬件回放根 | 同一套 L1–L4 代码，三个根启动出三种系统 |
| P4 决策与监管 | 引入行为树决策 + X1 四件套（心跳/诊断/安全门/任务管理） | 能通过 service 启停功能；故障能触发降级且可审计 |
| P5 多兵种复用 | 第二个兵种只用"新 YAML + 新装配根 + 少量新驱动"接入 | 复用度量：新增兵种改动行数占总量 < 10% |
| P6 效率收口 | 实时域划分、进程内组合、零拷贝、QoS 档位落地 | 高频链路无跨进程序列化；关键环延迟达标且可测 |

**复用度量建议**（把"复用程度高"变成可测指标）：
`新增兵种改动行数 / 总行数`、`跨层反向依赖数（应为 0）`、`可独立测试模块占比`、`策略改动的重编译次数（应为 0）`。

- **解耦可持续 = CI 校验依赖方向 + 模块独立可测 + 策略数据化**

## 14. 3v3 版骨架（裁剪后的内容清单）

```
R  装配根     sentry_root · infantry_root（2 台步兵若仅参数不同 → 同一根 + 不同 namespace）
L5 决策仲裁   最小状态机（巡逻/追击/生存/回血）+ 一道指令安全门

              目标感知(敌方装甲板)   ── 环境感知按场地实情增减

              上行中间件端口（保留，但无需多机协同语义）

```

## 15. 区域赛特性对优先级的重排

| 区域赛特性 | 架构含义 |
|---|---|
| **单败淘汰、容错极低** | **X1 可靠性 > L4 功能精度**。先保证"不死机、不失控、能急停"，再谈命中率 |

# 第三部分：三项架构决议（2026 规则与团队定位）

> 本部分**部分覆盖**第二部分。被推翻的条目在 §18 明确声明，不静默修改。

## 17. 三项决议及其架构后果

### 17.1 决议一：基于内置地图导航，激光仅用于定位

**陈述**：导航规划基于机内预置地图（离线构建、随资源包分发）；激光雷达**只服务定位**，不参与避障、地形分析或代价地图构建。

#### 17.1.1 直接删除的组件

| 原组件 | 处置 | 原因 |
|---|---|---|
| `terrain_analysis` / `terrain_analysis_ext` | **删除** | 唯一职责是把点云转成可通行代价；激光已不承担该职责 |
| `IntensityVoxelLayer`（PB 自定义 costmap 插件） | **删除** | 消费 `terrain_map` 的 intensity，链路已断 |
| `pointcloud_to_laserscan` | **删除** | 仅为建图模式服务；地图改为离线构建 |
| `slam_toolbox` 在线 SLAM | **删除**（仅保留离线建图工具） | 地图是离线资产，赛时不跑 SLAM |
| `ign_sim_pointcloud_tool` | **保留** | 仿真仍需点云喂 LIO，定位链路不变 |
| `point_lio` · `loam_interface` · `sensor_scan_generation` | **保留** | 状态估计链与 TF，定位刚需 |
| `small_gicp_relocalization` | **升级为核心** | 从"可选重定位"变为唯一定位手段 |

#### 17.1.2 关键洞察：内置地图把「定位」与「敌情检测」合并成一条流水线

这是本决议最大的架构红利，也是"过剩点云"价值的真正来源：

```
实时点云 ──配准──► 内置先验地图
                    ├──► 位姿 T          = 定位
                    └──► 配准残差 {p}    = 动态物体集合
                                          （地图里没有的点 = 场上会动的东西）
```

**配准残差即动态障碍。** 不需要额外避障传感器，不需要视觉就能得到"场上有人"的原始信号，
而这条流水线**几乎零成本**——配准本来就要为定位而做。

但残差给出的是**无标号的"动态物体"集合**：己方队友 + 敌方 + 场地可动元素（弹丸、机关）。
**如何区分敌我？** —— 恰好由决议三闭环解决：**队友广播自身位置，从残差中减去己方，剩余即敌方。**

> 三项决议在此形成设计闭环：内置地图 → 残差 → 需要区分敌我 → 兵间通讯提供己方位置 →
> 得到敌方态势 → 共享给步兵做半自动攻击。
> **这也解释了规则为何把"态势节点"的角色交给哨兵：它有地图，所以它能算出"什么不该在那儿"。**

#### 17.1.3 由此强制的四条契约

1. **地图是契约资产，不是配置文件。**
   - 版本化，与赛季规则版本绑定：规则改场地 → 地图必须换版。
   - **2D 栅格图与 3D 先验点云必须同源、同坐标系、同原点**——否则重定位与规划对不上，这是最隐蔽的坑。
   - 纳入 X2 接口契约面管理。

2. **场地坐标系原点必须全队统一。**
   - 这是决议三的**前提**。若哨兵与步兵地图原点不同，共享坐标毫无意义（会变成"幽灵敌人"）。
   - 建议原点直接对齐**规则定义的场地原点**，而非"机器人启动位置"。

3. **定位升级为安全关键服务。**
   - 激光只做定位 ⇒ **定位是单点故障**：定位漂移或丢失，导航与态势同时失效。
   - 定位模块必须对外提供**健康契约**：位姿 + **置信度/协方差** + 新鲜度 + 失效标志。
   - 这也是 §13 第 6 项（X1 收敛为两件）被部分推翻的原因——**定位健康必须进 X1**。

4. **需要"地图过期"与"动态物体"的区分机制。**
   - 场地若有可动元素，残差中会长期存在固定误报。
   - 需要：残差聚类 + 持续时间判定 + 先验的"允许动态区域"标注。

### 17.2 决议二：分层决策——顶层 RL，底层状态机/行为树

学术上对应 **Options Framework / 分层强化学习**：高层在"时序延展动作（option）"上决策，
每个 option 自带底层策略与终止条件。工程上这是**最务实**的形态——RL 决定"选什么"，
经典方法负责"怎么安全地做到"。

#### 17.2.1 建议细化为三层（而非两层）

| 子层 | 频率 | 职责 | 技术 |
|---|---|---|---|
| **L5-a 战术层** | **1–5 Hz** | 选技能 / 设定子目标 | **RL**（策略网络推理） |
| **L5-b 技能层** | 10–50 Hz | 把技能展开为可执行行为序列；**强制安全包络与前置条件** | 状态机 / 行为树 |
| **L4 执行层** | 100–1000 Hz | 跟踪与伺服 | 自瞄、导航控制器 |

> 分层的物理依据是**时间尺度分离**，不只是逻辑分层。若三层频率接近，那不是分层，只是拆文件。

#### 17.2.2 动作空间设计（决定成败的第一步）

| 方案 | 评价 |
|---|---|
| **离散技能选择**：`巡逻 / 追击 / 撤退 / 防守 / 回血 / 压制` | ✅ **推荐起点**。维度低、语义清晰、可解释、可屏蔽、易于 sim2real |
| 技能 ID + **离散目标区域**（区域枚举） | ✅ 第二阶段扩展，表达力更强而动作空间仍有限 |
| 连续子目标位姿 | ⚠️ 较难，需底层规划器兜底 |
| 直接输出速度 / 云台角 | ❌ **禁止**：不可解释、无法保证安全、sim2real 极难、无法审计 |

#### 17.2.3 五条工程红线（RL 项目最容易翻车之处）

1. **安全包络由下层强制，而非由 RL 自觉。**
   技能层与 X1 安全门**有权拒绝或裁剪** RL 输出。RL 输出的是**意图**，经校验后才成为指令。
   手段：**动作屏蔽（action masking）**——技能前置条件不满足则屏蔽该动作。
   ⚠️ **屏蔽逻辑必须在训练时同样生效**（masked policy），否则训练-部署不一致。

2. **状态编码器必须是纯函数，训练与部署共用同一份代码。**
   最大的工程坑：训练时状态多为**真值**，部署时是**估计值 + 噪声 + 缺失**。
   ⇒ 训练时必须注入**同等观测噪声与随机缺失（observation dropout）**，否则实车必然失效。
   ⇒ 状态编码器应放在 L3 作为纯函数，仿真环境与实车共同引用。

3. **奖励函数依赖的量可以训练专用，但状态必须全部可观测。**
   若状态含部署时拿不到的字段，策略必然学到虚假相关。

4. **必须保留纯规则基线，且 RL 能一键切回。**
   赛场"RL 抽风"不可接受。上线门槛：**RL 在仿真中稳定显著优于规则基线**才允许接管。
   推荐四阶段：**规则基线 → 规则+RL 离线评估 → RL 影子模式（跑但不控） → RL 接管**。
   影子模式是低成本低风险的验证手段，**强烈建议不要跳**。

5. **决策必须可记录、可回放、可审计。**
   RL 模块记录 `(state, action, mask, value/prob)` 并入 X4。
   否则赛后无法回答"它为什么这么决策"——在赛场上等于不可调试。

#### 17.2.4 需要提前评估的 ROI

RL 需要**大量并行、可快速步进的仿真**。Gazebo 的开销通常不足以支撑训练吞吐，
可能需在"自研轻量环境 / 无渲染步进 / 更高性能仿真器"之间抉择。**这是一笔大投入。**

建议策略：**先把 RL 的"接口与舞台"建好**（状态编码器 + 动作空间 + 安全屏蔽 + 影子模式记录），
算法本身先用最简方案（离散动作空间上的 PPO / DQN 足够）。
把工程力气花在**环境保真度与训练-部署一致性**上，而不是算法复杂度上。

### 17.3 决议三：兵间协同——态势共享与步兵半自动攻击

**陈述**：2026 规则允许机器人之间通信；哨兵富余的激光点云可用于全局"敌我态势共享"，
并允许步兵进行半自动决策攻击。

⚠️ **本条撤销第二部分 §13 第 1 项。** 我当时依据"3v3 无雷达站"判断机间通信可降级为一条串口——
**该前提被新规则推翻**。第一轮方案中"横向 I/O + 态势语义 + 契约"三分的设计**恢复有效**，
且必须按**分布式系统**对待，而非一条数据线。

#### 17.3.1 架构定位：哨兵成为队伍的「态势节点」

结合决议一，哨兵拥有别人没有的两样东西：**内置地图** 与 **激光雷达**。
因此它的天然角色是队伍的信息源。

```
哨兵: 激光 ─配准→ 位姿 + 残差(动态物体)
                             │
队友: 各自广播自身位姿 ────────┤ 减去己方
                             ▼
                        敌方态势 (带时间戳 + 置信度)
                             │
                    ┌────────┴────────┐
                    ▼                 ▼
              哨兵自身决策        步兵半自动攻击
              (态势向量)         (外部目标注入)
```

#### 17.3.2 五条设计原则

1. **共享"态势语义"，不要共享原始点云。**
   这是最容易犯的错：原始点云带宽爆炸，且队友拿到的是一堆无标号的点。
   ⇒ 哨兵在**本地**完成"残差 → 聚类 → 敌方位置/朝向/置信度"的语义提取，**只广播语义结果**。
   带宽分级（由省到费）：`敌方位置+置信度` ≪ `占据栅格增量` ≪ `降采样点云` ≪ `原始点云`。
   > 你的表述"过剩点云可用于态势共享"方向正确，但工程落地应为
   > **"点云只在本地消费，对外广播的是它提炼出的态势"**。

2. **一致性模型是"最终一致 + 时间戳 + 置信度"，不是强一致。**
   每条态势带 `stamp` 与**有效期 TTL**，过期即衰减失效。别让 200ms 前的敌情误导当前决策。

3. **时钟必须跨机器人对齐。**
   共享位置若时间错位，就会变成"幽灵敌人"。X3 时间同步面**范围扩张**：从机内扩到机间。
   统一场地坐标系（§17.1.3-2）是其前提。

4. **能力声明与版本协商。**
   队友可能跑不同代码版本。需握手交换**能力集与协议版本**，不支持则优雅降级。
   态势消息必须**向后兼容**（新增字段不破坏旧解析）。

5. **机间通信绝不在实时路径上。**
   场地 WiFi 丢包、抖动、重连是常态。其抖动**不得影响控制环**。
   定位：异步、best-effort、非阻塞；**本地感知优先级永远高于共享信息**。

#### 17.3.3 步兵半自动攻击：目标来源变为「多源融合」

这是决议三对 L3/L4 最实质的改动。

原架构中 `auto_aim` 目标来自**自身视觉**（单一来源）。半自动攻击引入**外部目标源**（哨兵共享态势），
于是 `auto_aim` 的目标输入必须变成**可插拔的多源融合**：

| 目标来源 | 特性 |
|---|---|
| 自身相机（装甲板识别） | 高精度、低延迟、**视野受限** |
| 哨兵共享态势 | 覆盖广、**精度低、有延迟** |
| 队友共享 | 同上，且来源可能重复 |
| 裁判系统 | 无位置，仅有血量/状态 |

**因此 L3 必须新增"目标融合与置信度仲裁"**：多源去重、坐标统一、时间对齐、置信度加权。
`auto_aim` 只消费融合后的目标、不关心来源——这样它才能同时服务"自己看见"与"别人告诉我"。

#### 17.3.4 安全红线（已定：开火必须人工授权）

**决议**：步兵**必须由操作手进行开火授权**，不存在自动开火。完整安全语义见 §22。

要点（该判据属 X1 安全门，**不得由 RL 或视觉模块自行放宽**）：
- 安全要求从"自动开火门限"转移为：**禁止把友军作为瞄准目标** + **呈现必须保真**。
- 共享信息可能出错（残差误检、队友位置过期、坐标错位），因此 IFF 必须取**保守取向：宁可漏报，不可误报**。

## 19. 更新后的骨架

```
R  装配根        sentry_root · infantry_root（各兵种：生产根 ∥ 调试根 ∥ 回放根）

L5 决策与仲裁    分三层：
                 L5-a 战术层  RL (1–5Hz)  ── 输出：技能ID(+区域参数)
                 L5-b 技能层  状态机/行为树 (10–50Hz) ── 展开 + 前置条件 + 安全屏蔽
                 L5-c 安全门  指令仲裁(谁有权控制底盘/云台/发射；开火门限/IFF)

L4 功能应用      自瞄(多源目标注入) · 导航(静态地图规划 + 动态障碍规避)

                 · 地图管理(2D栅格 + 3D先验点云，同源同坐标系，版本化) ★契约资产
                 · 动态物体检测(配准残差 → 聚类)
                 · 态势融合(多源目标去重/坐标统一/时间对齐/置信度仲裁) ★新增
                 · 目标感知(装甲板视觉)
                 · 状态估计(里程计)          ← 环境感知(地形) 已删除

L2 I/O 抽象      · 下行 HAL：底盘/云台/发射机构 · 裁判系统串口 · 传感器(激光/IMU/相机)
                 · 上行中间件端口
                 · 横向协同端口(机间通信) ★恢复：能力声明/版本协商/带宽预算/降级

L1 平台基础      时间时钟 · 数学滤波 · 参数系统 · 日志录制 · 错误码
                 + 状态编码器纯函数(训练与部署共用) ★新增

X1 健康安全      心跳/存活 · 急停硬路径 · ★定位健康 · ★开火安全门(IFF/置信度)
X2 接口契约      机内接口 + ★机间协议 + ★地图版本
X3 时间同步      机内同步 + ★跨机器人时钟对齐
X4 可观测调参    原有 + ★RL 决策记录(state/action/mask/value)
X5 分布式协同    ★新增：带宽预算 · 能力声明与版本协商 · 队友上下线降级 · 态势一致性模型
```

## 20. 当前应优先冻结的三份契约

按"不定则返工"的严重程度排序：

1. **世界模型接口**（L3 → L5/L4）
   态势向量的字段与语义。它同时被 RL（状态输入）、导航（动态障碍）、自瞄（目标）消费，
   且**必须能被仿真环境复现**。这份契约不定，RL 无法训练。
2. **决策产物接口**（L5-a → L5-b → L4）
   技能 ID 枚举 + 参数格式 + 前置条件定义 + 安全屏蔽规则。
   它决定 RL 的动作空间，也决定底层能否强制安全包络。
3. **机间态势协议**（哨兵 ↔ 步兵）
   消息字段、单位、坐标系、时间戳与 TTL、置信度、版本与能力协商、降级行为。
   **必须由哨兵与步兵两个代码库共享同一份定义**（独立接口包）。

> 共同特征：**跨模块、跨进程、甚至跨机器人**，且**变更成本随开发推进急剧上升**。
> 其余接口可在实现中演进，这三份不行。

## 21. RL 决策层可行性评估（决策记录）

### 21.1 结论先行

**不建议在区域赛周期内让 RL 进入实车控制回路。** 建议：

| 阶段 | 做法 |
|---|---|
| **现在（区域赛周期）** | L5-a 用**可解释的打分函数 / 状态机**实现，但**把 RL 的位置（接口）留出来** |
| **区域赛后** | 以**影子模式**零风险验证 RL 是否有价值 |
| **仅在证明价值后** | 限定场景接管 + 一键切回 |

核心理由：**RL 在本场景的收益上限受"状态质量"约束，而其工程代价与风险落在关键路径上。**

### 21.2 L5-a 要解决的到底是什么问题

形式化之后是：**部分可观测 + 多智能体 + 稀疏奖励**——强化学习中最难的一类。

| 特性 | 在本场景的体现 |
|---|---|
| **部分可观测** | 敌方位置来自配准残差 + 兵间共享，有**噪声、延迟、缺失** |
| **多智能体** | 对手也在决策，环境非平稳，策略会互相追逐 |
| **稀疏奖励** | 真正的奖励只有"赢/输"；"击杀""掉血"都是中间代理奖励，而 **reward shaping 本身就是调参无底洞** |

### 21.3 优势（公平陈述）

| 优势 | 成立前提 |
|---|---|
| 学到跨时间尺度的权衡（如"放弃追击去回血，因为 30 秒后有加成"） | 状态可靠 + 仿真保真 |
| 对手自适应 | 需对手建模或 self-play，工程量再翻倍 |
| 减少阈值手工调参的人力 | 换成奖励设计与训练调参，人力未必更少 |
| 理论上限高于手工规则 | 上述前提全部成立 |

> **关键：四条优势全部依赖"状态可靠 + 仿真保真"。而这两点恰是本项目最不确定的部分。**

### 21.4 代价与风险

**a) 工程代价远超"训练一个网络"**

完整清单：并行快速仿真环境 · 状态编码器（sim/real 共用） · 观测噪声建模 · 奖励设计与调参 ·
训练基础设施（GPU / 并行环境 / 实验管理） · 推理运行时（ONNX/TensorRT） · 模型版本管理 ·
影子模式 · 回退开关 · 策略行为可视化与失败案例分析工具。

> 量级判断：这是一条**独立的、需要专人长期负责**的工程线，不是"顺便做一下"。
> 对一支 ROS2 尚在起步、导航组 4–6 人的学生队，它会直接占用关键路径的人力。

**b) 最大技术风险：仿真里 90 分，实车 0 分**

失败模式非常具体：仿真中状态多为**真值** → 策略学到依赖精确状态；实车状态有噪声与缺失 →
**输入分布偏移** → 输出荒谬动作。而且**赛前很难发现**，因为仿真里表现完美。

**c) 可验证性问题（对单败淘汰最致命）**

- 状态机出错：看日志就知道"卡在状态 3"，几分钟定位。
- RL 出错：无法快速区分是**感知问题**还是**策略问题**，可能整晚调不出来。
- **赛场上的可调试性 > 理论最优性。**

**d) 人才与传承风险（直接威胁原始目标）**

学生团队每年换届。状态机看代码就懂逻辑；RL 的知识高度集中在训练者手里。
换届后若此人离开，这套东西**无人可维护**——这与"可持续发展"直接冲突。

**e) 机会成本**

关键路径已定：内置地图 + 定位 + 态势融合 + 兵间通讯 + 半自动步兵 + 自瞄。
这些是"必须做且已确定"的；RL 是"可选且高风险"的。**投人力到 RL = 从关键路径抽血。**

### 21.5 推荐路径（风险递增，每步都可独立止损）

| 阶段 | 做什么 | 风险 | 前提 |
|---|---|---|---|
| **0 现在** | L5-a 用打分函数/状态机；**状态编码器做成纯函数** | 零 | — |
| **1 区域赛后** | RL **影子模式**：跑但不控，记录 `(state, RL action, 规则 action, mask, value)` | 零 | §21.6 门槛检验通过 |
| **2 证明价值后** | 限定场景接管 + 一键切回 | 中 | 影子数据显示 RL 分歧处确实更优 |

**关键设计点：先定接口，后定算法。**

若 L5-a 的接口是「**态势向量进 → 技能 ID 出**」，那么**打分函数与神经网络是可互换的实现**。
⇒ 现在用打分函数（可解释、可调、可调试），将来换 RL 时**接口不变、上层不变、下层不变**。
⇒ **架构的关键是接口，不是算法。** 这正是原始目标"功能解耦 / 可扩展"的正解。

### 21.6 做 RL 之前必须先过的门槛检验（便宜且必要）

> **把规则基线放进仿真，看它的胜负率是否与实车表现相符。**
> 若仿真里规则表现与实车差异很大 ⇒ 仿真不可信 ⇒ RL 训练出的策略同样不可信。

这个检验**无论做不做 RL 都该做**，因为它同时服务导航线与感知线（仿真保真度是共同需求）。

### 21.7 更便宜的替代方案（若目标只是"减少手工调参"）

| 方案 | 说明 | 相对 RL |
|---|---|---|
| **效用打分（推荐起点）** | 每个技能算一个分数，取最高 | 结构上等价于 policy，极易调参与可视化 |
| **打分函数 + 离线参数优化** | 规则结构不变，用 CMA-ES / 贝叶斯优化在仿真里搜参数 | 工程量小一个数量级，保留可解释性 |
| **行为克隆 / 模仿学习** | 收集 `(state, action)` 数据做监督学习 | 无需奖励设计、无需探索，稳定得多；上限受数据质量限制 |

### 21.8 什么情况下 RL 才真的值得做

- ✅ 规则已到瓶颈，且能**量化**规则差在哪（有明确失败模式，且 RL 能覆盖）
- ✅ §21.6 仿真可信度检验**已通过**
- ✅ 有 **≥1 人愿意长期负责**（不是一个人的毕设/加分项）
- ✅ 具备并行仿真吞吐（数十环境并行）

❌ **不要因为"RL 是趋势 / 答辩好看 / 加学分"而做。**

### 21.9 对抗训练（Self-Play）方案评估

**提问**：用两个 RL 模型互相对打，或用**一个策略同时控制双方**进行自博弈对抗训练，
能否解决 §21 提出的问题？

#### 21.9.1 先肯定：这是"如果做 RL，正确的那条路"

自博弈确实解决了 RL 在本场景的两个**真实**难点：

| 难点 | 自博弈的作用 |
|---|---|
| **多智能体非平稳性** | 提供自动化、难度递增的对手课程——这是应对"对手也在学习"的标准解法 |
| **奖励设计** | 零和博弈下奖励可简化为"胜/负 (+1/−1)"，大幅降低 reward shaping 负担（AlphaZero 路线） |

> **方向判断是对的。** 但它解决的是"**怎么学**"，不是"**该不该学**"。

#### 21.9.2 它不解决 §21 的任何一条主要问题

| §21 的问题 | 自博弈是否解决 | 原因 |
|---|---|---|
| **a) 工程代价** | ❌ 反而**更高** | 额外需要：联赛/对手池管理、非传递性处理、绝对评估基准设施 |
| **b) 状态质量封顶收益** | ❌ **完全不解决** | 策略仍需观测状态。仿真给真值、实车给噪声 → 同样的分布偏移。且"完美观测"训练出的策略**更自信、更脆弱** |
| **c) 仿真 90 分实车 0 分** | ❌ **可能更严重** | 见 §21.9.3-a |
| **d) 可验证性** | ❌ **更差** | 现在是两个黑盒；"我的模型打败我的另一个模型"**不能说明能否打败对手战队** |
| **e) 人才与传承** | ❌ 更差 | 联赛训练基础设施更复杂，知识更集中 |
| **f) 机会成本** | ❌ 不变 | 关键路径照旧被抽血 |

#### 21.9.3 自博弈引入的三个新问题

**a) 对抗训练会主动寻找并放大仿真器缺陷（simulator exploits）**

这是 self-play 特有、且比单模型训练**更严重**的风险：
两个策略都在优化 ⇒ **任何仿真漏洞都会被主动发现并利用**。

例：仿真弹道模型若与实车不同，两个策略会**共同进化出"只在仿真里有效"的射击习惯**。
单模型训练时这种漏洞可能不被触发；对抗训练则**专门去触发它**。

⇒ 对仿真保真度的要求从"较好"上升到"**必须可信**"——这正是 §21.6 门槛检验要回答的问题。

**b) 非传递性（Non-transitivity）**

自博弈中策略可以循环：A 胜 B，B 胜 C，C 胜 A（剪刀石头布）。
⇒ "最强策略"**没有良定义**。需要**联赛（league）+ 多样化对手池**（AlphaStar 式）缓解。
⇒ 这又是一块独立工程量。

**c) 对抗双方在物理上并不对称 —— 对手不是你自己**

自博弈的隐含假设是**双方能力对等**（围棋/象棋成立）。
但 RM 里：**对手的机器人不是你的机器人**——速度、命中率、血量管理、机械可靠性都可能不同。
⇒ 自博弈训练出的对手是"**你自己的镜像**"，是真实对手的**劣质代理**。

若走这条路，必须加入**对手能力域随机化（domain randomization）**：
随机化对手的速度、命中率、反应延迟、血量乃至战术风格，使策略学到**鲁棒**而非"针对自己"。
⇒ 又一块额外工程量，且随机化范围需经验设定。

#### 21.9.4 最关键的 ROI 论证：战术层在胜负权重中排第三

这一点比"RL 难不难"更重要。

**RM 3v3 胜负的决定因素（按权重）**：

| 权重 | 因素 | 归属 |
|---|---|---|
| **第一** | **命中率**（自瞄精度、弹道、云台控制） | 视觉组 / 电控组 |
| **第二** | **机械与电气可靠性**（不炸、不断连、不卡弹） | 机械组 / 硬件组 |
| **第三** | **战术与决策**（走位、目标选择、时机） | ← **RL 优化的正是这一层** |

⇒ **命中率 35% + 战术平庸的队伍，会稳定战胜命中率 20% + 战术优秀的队伍。**
⇒ 因此**顶层策略的边际价值，被机械与瞄准的噪声下限所封顶**。

**结论**：在自瞄与可靠性尚未触及瓶颈之前，投入 RL 的边际收益**低于**把同样人力投入命中率与可靠性。
该判断与 RL 技术本身无关，纯粹是 ROI 层面。

#### 21.9.5 一个更好的用法：让 RL 当"红队"，而不是当"控制器"

如果兴趣在于**对抗训练本身**（这确实是很有技术含量的方向），有一个**风险为零、价值明确**的用法：

> **把 RL 当作对手生成器 / 对抗性测试器，用来发现规则策略的盲区。**

| 维度 | RL 当控制器 | **RL 当红队（推荐）** |
|---|---|---|
| sim2real 迁移 | **需要**（最大风险） | **不需要** ← 关键优势 |
| 实车运行 | 需要 | 不需要，可只在仿真里跑 |
| 可解释性 | 需要 | 不需要 |
| 安全包络 | 严格需要 | 不需要 |
| 产出 | 一个黑盒策略（能否用不确定） | **一份"规则在哪会输"的清单（确定可用）** |

**为什么这个用法好得多**：

- **不需要 sim2real**：红队永远待在仿真里；仿真不可信也不影响它发现"**仿真内的规则弱点**"
- **不需要安全与可解释**：它是测试工具，不是控制器
- **产出是知识而非依赖**：它告诉你规则在什么局面会输，你用规则去修补
  ⇒ **产物沉淀在你们的规则库里，不随人员换届流失**
- **对主线零干扰**：可并行低优先级推进

**典型产出示例**：
`在己方双步兵阵亡、哨兵残血且比赛剩余 <60s 时，规则策略胜率显著低于 RL 对手`
⇒ 这是一条**可直接修补的规则条目**。

#### 21.9.6 若仍决定做自博弈，最小可行设计

| 项 | 要求 |
|---|---|
| 策略结构 | **单策略控制双方**（对称自博弈），比两个独立模型更省样本 |
| 仿真环境 | **无渲染、可并行、快速步进**的 3v3 **对局**仿真（含弹道/伤害/血量/弹药/回血/比赛阶段） |
| 观测模型 | 必须注入与真实感知**同等的噪声、延迟、缺失**（否则策略无法迁移） |
| 对手随机化 | 随机化对手速度/命中率/反应延迟，避免"只针对自己" |
| 对手池 | 联赛机制，保留 3–5 个历史检查点，缓解非传递性 |
| 评估锚点 | **必须**有绝对基准：规则基线 + 真实对练记录。**仅看自博弈胜率无意义** |
| 部署 | **第一年只允许影子模式**（跑但不控） |

#### 21.9.7 决策建议

| 方案 | 建议 |
|---|---|
| RL 直接当控制器上线 | ❌ 区域赛周期内不建议 |
| 自博弈训练控制器 | ⚠️ 技术方向正确，但 ROI 与工程量在区域内均不成立 |
| **RL 当红队做对抗性测试** | ✅ **推荐**：零 sim2real 风险，产出可沉淀为规则 |
| 不做 RL，打分函数 + 离线参数优化 | ✅ **最稳**（§21.7） |
| 无论选哪条，先做 §21.6 仿真可信度检验 | ✅ **必须** |

> **一句话**：你的自博弈想法是"做 RL 的正确姿势"，但它解决"怎么学得更好"，
> 而你的瓶颈是"**该不该学**"与"**状态够不够准**"。
> 把它转向"红队"用途，能保住这个方向的技术价值，同时避开全部致命风险。

## 22. 步兵开火授权的安全语义（已定：必须人工授权）

**决议**：步兵**必须由操作手进行开火授权**，不存在自动开火路径。

### 22.1 安全责任转移了，但约束没有消失

人工授权把"开火决策"交给操作手，但引入新的关键约束：

> **操作手是根据系统呈现的信息做判断的。若呈现误导，操作手仍会误伤。**

⇒ 安全要求从"自动开火门限"**转移为两条**：

1. **禁止把友军作为瞄准目标** —— `auto_aim` 的目标源必须**过滤**友军，而不只是"标记"友军。
   （自动瞄准会自动把云台转向目标；指向友军毫无价值且危险，因为操作手可能误按授权。）
2. **呈现必须保真** —— 敌我身份与置信度必须清晰、不可混淆。

### 22.2 代价不对称 ⇒ IFF 必须保守

在有人的环里，两类错误的代价**严重不对称**：

| 错误类型 | 后果 | 代价 |
|---|---|---|
| **漏检敌方**（假阴性） | 操作手少打一个目标 | 小 |
| **误报友军为敌方**（假阳性） | 操作手可能误伤友军，且**从此不再信任系统** | 极大 |

⇒ **IFF 与目标呈现必须取保守取向：宁可漏报，不可误报。**
低置信度目标**不得**以"确定敌方"的方式呈现。

### 22.3 由此新增的架构需求：操作手信息呈现契约（HMI）

原骨架缺这一块，现补：

| 需呈现 | 要求 |
|---|---|
| 目标位置 / 朝向 | 实时更新，**带 TTL 可视化**（过期目标必须明显标出） |
| **敌我身份** | 必须显著，不可与目标框混淆 |
| **置信度** | 低置信度必须与高置信度**视觉可区分**，不能同款呈现 |
| **信息来源** | 区分"自己相机看见" vs "哨兵共享"（操作手需要知道可信度依据） |
| 授权状态 | 当前锁定目标是否已授权、授权是否仍有效 |

**归属**：**X2 接口契约面**（消息定义）+ **X4 可观测面**（呈现实现）。
且**呈现逻辑不得由 RL 或视觉模块自行决定**——它是安全相关契约。

### 22.4 授权的作用域（必须明确定义的安全语义）

操作手按下授权后，有一个必须澄清的问题：
**若云台随后扫到另一个目标，授权是否延续？**

| 语义 | 风险 |
|---|---|
| 授权绑定"当前锁定"（一次授权持续有效） | ⚠️ 目标切换后可能误打新目标 |
| **授权绑定"具体目标身份"，目标切换即失效** | ✅ **推荐** |

⇒ 建议：**授权与目标身份绑定**；目标丢失或切换 → 授权自动失效 → 需重新授权。
语义上类似"**扳机保持**"而非"一次授权"。

### 22.5 延迟要求的放宽与保留

- 人在环 ⇒ 允许数百毫秒级端到端延迟，**决策与态势的实时性压力下降**。
- 但 **信息时效必须可视化**：过期态势不得静默使用（TTL 必须在 §17.3.2 的机间态势协议中定义）。
- `auto_aim` 自身的**跟踪环仍是硬实时**（§7 实时域划分不变）。

| 原条目 | 更新后 |

| "绝不能在低置信度下**自动开火**" | 自动开火已排除出范围 → 改为"**绝不能在低置信度下瞄准/锁定**" |
